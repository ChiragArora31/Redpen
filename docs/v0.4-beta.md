# v0.4 beta: validate value, then widen distribution

## Release intent

Make task verification part of the coding conversation, and make bugfix evidence stronger than “a test file changed.” Focus on Codex developers who regularly review agent-generated changes. Do not position this as an AI correctness judge or promise universal regression support.

## Human steps remaining

1. Install/enable the local plugin in your actual Codex client; review and trust the hook. Run one real bugfix from start to final receipt. Confirm automatic completion capture, not just manual check output. Client availability and hook trust belong to your account.
2. Invite ten developers personally. Ask each to use it on a real task and show where the workflow gets in their way. Do not substitute stars/downloads for users or invent testimonials.
3. Record the demo and a real interactive handoff. Share only permissioned/redacted receipts; no private repo transcripts.
4. Publish the prepared npm version if account login/passkey approval is requested. Do not publish before the test/package gates pass.
5. After beta validation, use the official plugin submission portal. Complete any developer identity/account verification, upload the reviewed package/assets, and obtain review. A local install is not a directory approval. Do not add a hosted MCP backend merely to satisfy a different submission flow.

Invitation draft:

> I'm building Redpen because I keep checking whether an agent's “done” actually means done. It now runs inside a Codex workflow and returns an evidence receipt. Would you try it on one real task this week? I'd like to watch where it's useful and where it gets in the way—not ask you for a promotional testimonial.

## What to measure manually (no telemetry)

- time from install to first task/receipt, and where installation fails
- how many explicit Redpen commands the developer has to type
- whether it catches a false completion or saves review time
- whether an UNVERIFIED result makes sense to the reviewer
- whether the developer voluntarily uses it on a second task within a week

Record consented observations in a private sheet, not this repository. Ten installations without repeat use are not product validation. Prioritize the next release from recurring pain in these sessions, not a feature-count target.

## Release gates

```bash
npm ci
npm run check
npm test
npm run demo:cases
npm pack --dry-run
npm run smoke:package -- --codex
node dist/cli.js --help
node dist/cli.js --version
```

Verify the built tarball in a temporary prefix before publication. Existing `.redpen/` session/report files must not ship. npm approval, developer outreach, hook trust and directory submission are the only intended human handoffs.
